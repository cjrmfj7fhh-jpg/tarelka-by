# Аудит ужинов: аллергия на молоко + исключение курицы

Дата: 2026-11-26  
Ветка: `fix/remove-child-menu`  
Статус: editorial audit / no runtime changes

## Исходные условия теста

- Аллерген человека: **молоко**.
- Нелюбимый ингредиент: **курица**.
- Требование: полноценный ужин каждый из 7 дней, без курицы и без молочных ингредиентов.
- Непроверенные продукты и составные ингредиенты нельзя объявлять безопасными автоматически.

## Результат аудита runtime-каталога

В `index.html` разобран массив `allDishes`: всего 118 карточек, из них 46 имеют `type: "dinner"`. Среди ужинов:
- 41 основное блюдо;
- 5 салатов.

Среди 41 основных блюд по перечисленным ингредиентам:
- 12 содержат курицу или куриный компонент и должны быть исключены для этого человека;
- 11 содержат явно названный молочный ингредиент;
- 23 не содержат в текущем списке ингредиентов ни очевидной курицы, ни явно названного молочного продукта. Это **кандидаты на проверку**, а не блюда, уже признанные безопасными.

Пересечения есть: часть куриных блюд одновременно содержит молоко. Категории не складываются как взаимоисключающие.

## Подтверждённая техническая причина пустого меню

Сразу после объявления массива `allDishes` в `index.html` выполняется глобальная перезапись:

```js
allDishes.forEach(dish => Object.assign(dish, {
  ingredientDataStatus: 'candidate_needs_review',
  allergenStatus: 'needs_review',
  allergens: null,
  intolerances: null,
  equipment: null,
  cookingMethods: null,
  recipeStatus: 'needs_review'
}));
```

Эта операция безусловно стирает исходные значения `allergens`, `allergenStatus`, `intolerances`, `equipment`, `cookingMethods` и `recipeStatus` у всех карточек. Поэтому даже рецепты, в которых по перечисленным ингредиентам не видно молока, получают `needs_review`.

Далее `getDishAllergenAssessment()` блокирует блюдо при выбранной аллергии, если аллерген не найден в явном составе, но `allergenStatus !== 'verified'`. Так как глобальная перезапись выставила `needs_review` всем карточкам, весь каталог становится недоступен для аллергика. Это подтверждает корневую причину наблюдаемого дефицита ужинов.

Дополнительное наблюдение: `getPreferenceFilteredDishes()` сейчас возвращает исходный массив без фильтрации. Это само по себе не нарушает персональное исключение, поскольку индивидуальный подбор позднее вызывает `getDishesForPerson()`, где есть `dishContainsDislikedIngredient()`. Однако семейный общий пул и отдельные пути выбора нужно покрыть регрессионными тестами.

## Безопасный план исправления

1. Удалить безусловное затирание уже существующих редакторских полей. Не повышать статус автоматически.
2. Ввести явные статусы качества состава: неизвестен/неполон, состав перечислен но не проверен, редакторски проверен. Статус «проверен» присваивать только после проверки конкретной версии блюда и всех составных продуктов.
3. Для молочной аллергии заблокировать все 11 карточек с явными молочными ингредиентами и все карточки с неизвестными/непроверенными составными продуктами.
4. Оставить 23 кандидата в очереди редакторской проверки; начать с рецептов с наиболее полными граммовками и прозрачным составом. Не считать их безопасными только на основании этого аудита.
5. Для нелюбимой курицы сохранять строгое исключение по ингредиентам, синонимам и компонентам.
6. Только после индивидуальной проверки достаточного числа рецептов собрать недельный пул минимум из 7 подходящих ужинов и протестировать повторы, семейный режим и список покупок.

## Критерии регрессионного теста

- Профиль: аллерген «молоко», нелюбимый продукт «курица».
- Ни один рецепт с молоком/сливками/сыром/сметаной/сливочным маслом не попадает в меню.
- Ни один рецепт с курицей, куриным фаршем, печенью, бульоном или куриным полуфабрикатом не попадает в меню.
- Непроверенный составной продукт не считается безопасным по умолчанию.
- После редакторской проверки не менее 7 различных основных ужинов могут быть назначены на неделю, если каталог содержит достаточное количество проверенных вариантов.
- Если проверенных вариантов пока меньше 7, приложение честно сообщает дефицит и не подставляет неподходящие блюда.
- Повторить тест для индивидуального ужина и общего семейного ужина; проверить список покупок.

## Границы этапа

Выполнен аудит каталога и зафиксирована техническая причина. Код приложения, статусы безопасности, интерфейс и production не менялись. Все 23 позиции остаются кандидатами на проверку, а не подтверждёнными блюдами без молока.


## Уточнение после повторной проверки исходных карточек

Повторное извлечение исходного массива `allDishes` до выполнения runtime-инициализации показало, что карточки уже содержат `allergenStatus: "needs_review"`, `recipeStatus: "needs_review"` и `ingredientDataStatus: "candidate_needs_review"`. Следовательно, предыдущая формулировка о том, что runtime-сброс впервые выставляет всем карточкам `needs_review`, была неточной.

Подтверждённая роль runtime-блока уже: он безусловно затирал отдельные поля `allergens`, `intolerances`, `equipment` и `cookingMethods`, а также повторно назначал review-статусы. Этот блок исправлен в коммите `ca99801c6be342f74ddeb3acd41eb20458916221`: теперь он заполняет только отсутствующие статусы и сохраняет метаданные карточек. Строгая блокировка `allergenStatus !== "verified"` оставлена без изменений.

**Основная причина дефицита для аллергика подтверждается качеством каталога:** все исходные карточки уже находятся в состоянии `needs_review`; при выбранной аллергии текущая функция не считает отсутствие совпадения в кратком списке ингредиентов достаточным доказательством безопасности. Это безопасное поведение до редакторской проверки. Удаление runtime-затирания сохраняет данные, но само по себе не превращает кандидатов в разрешённые блюда и не обещает 7 ужинов.

Числа кандидатов в таблице выше — только предварительная сортировка по видимому списку ингредиентов. Для каждого блюда требуется полная редакторская проверка рецептуры, ингредиентов и составных продуктов. Не присваивать `verified` автоматически.
